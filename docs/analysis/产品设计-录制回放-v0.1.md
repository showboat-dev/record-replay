> 前置：`../refs/` 下 14 个参考仓库已就位 ｜ 分析报告：`playwright-分析.md`、`browser-use-分析.md`、`page-agent-借鉴点分析.md`

## 0. 一句话定义

**一个「录制一次、稳定回放 N 次」的网页自动化产品：录下来的不是代码，而是一份带多级定位信息的动作轨迹（action trace）；回放时按「确定性优先、AI 兜底」的阶梯逐级解析元素，失败自动降级并写回学习。**

差异化不是"能录"，而是三件事：

| 对比对象 | 它的做法 | 它的死穴 | 我们的做法 |
|---|---|---|---|
| **Playwright codegen / Chrome DevTools Recorder** | 录 selector 字符串 → 回放重新 query | 回放时解析不出元素就失败；iframe/closed shadow/canvas 录不到 | 录**元素包**（指纹+语义+几何+截图+frame 链），回放**多级降级**，失败可自愈 |
| **midscene** | 录自然语言描述 → **每步都走 AI** | 慢、贵、不确定（每步秒级 + 模型波动） | **确定性优先**：常规步骤毫秒级本地解析，AI 只在解析失败时介入 |
| **UI.Vision / RPA** | 录坐标 + 视觉模板 | 换分辨率/布局就挂，无法解释 | 坐标和视觉是**最后两级兜底**，前三级都用语义 |

> 产品一句话卖点：**"录得下来，也跑得下去。"**

## 1. 为什么现成方案不够（把问题定义清楚）

1. **录制粒度太粗**：codegen 录 `page.click('css=#submit')`，命运全押在这一个选择器上。SPA 一次热更新、A/B 实验、动态 class，就断了。
2. **回放模型是"重新查找"而不是"重新认领"**：每次回放都在一个可能已经变了的页面上，重新执行一遍"找到它"。一旦有多个候选或零候选，就报错——而人其实知道"就是右上角那个蓝色按钮"。
3. **元素身份不存在**：录的是"位置/字符串"，不是"这个元素是谁"。Playwright 自己的 recorder 在生成 selector 时用的是打分启发式（testid≪role+name≪id≪nth），**它知道 nth 不可靠，却没有别的身份可用**。
4. **可解释性差**：失败时只有 `Timeout 30000ms exceeded`，用户不知道"卡在哪一步、看到了什么"。录制回放产品的口碑，一半取决于**失败时能不能自助排障**。

**我们的解法 = 换一个回放模型**：把"回放 = 重新查找"改成"回放 = 用一份证据链重新认领 + 认领失败就修"。

## 2. 产品形态（用户旅程）

```
① 录制      用户在受控浏览器里正常操作 → 后台自动生成 trace（可编辑）
② 编辑      改参数（把输入值改成变量）、加断言、加等待、合并/拆分步骤
③ 回放      本地/无头执行，实时看到每步：耗时、截图、命中级别（L1/L2/…/AI）、自愈标记
④ 自愈      失败步骤自动降级重试；AI 修复成功后把新候选写回 trace（版本 +1）
⑤ 回归      同一 flow 批量跑 N 次 / 多分辨率 / 多环境，出成功率报告与差异截图
⑥ 沉淀      通过率高的 flow 变成"资产"，可被其他 flow 引用（子流程）
```

**关键产品原则**：

- **录制不是终点，trace 是活的资产**：每次回放都在给 trace 加分（自愈写回、成功率统计）。
- **每一步都要可解释**：命中级别、耗时、截图、候选打分，全部可见。
- **默认不联网**：确定性回放完全本地；AI 兜底是**可选开关**（隐私红线，见 §11）。

## 3. 五个核心设计决策

| # | 决策 | 推荐 | 理由 |
|---|---|---|---|
| D1 | **录制发生在哪** | **受控浏览器**（我们启动的 Chromium），扩展模式二期 | 只有受控浏览器能拿到完整 CDP：OOPIF 注入、closed shadow（`DOM.getDocument(pierce)`）、trusted 事件、持久登录态。回放成功率优先于"在我自己的 Chrome 里录" |
| D2 | **录制产物是什么** | **JSON action trace**（不是代码） | `puppeteer/replay` 已经证明这个模型可行；代码只是导出格式；trace 才能被编辑、加断言、做 diff、自愈写回 |
| D3 | **回放引擎用什么** | **v0 直接用 Playwright 做执行层**，自研 recorder/resolver/verifier | Playwright 提供 actionability + auto-wait + 跨浏览器 + trace 能力（省半年）；我们的价值在 trace 模型和解析算法，不在重写 CDP |
| D4 | **解析策略** | **阶梯降级（L0→L4）**，前几级纯本地、毫秒级，AI 只做最后一级 | 兼顾速度/成本/鲁棒性，这是对 codegen 和 midscene 的双向改进 |
| D5 | **失败处理** | **失败必须产出可诊断 artifact**（每步 before/after 截图 + DOM/aria 快照 + 候选打分日志） | 抄 Playwright trace + browser-use 的 raw 存档思路；这是产品护城河 |

## 4. 架构（六层）

```
┌─────────────────────────────────────────────────────────────┐
│ 产品层   录制 UI / trace 编辑器 / 回放面板 / 回归报告        │
├─────────────────────────────────────────────────────────────┤
│ 编排层   Flow Runner：变量、条件、循环、子流程、重试、超时    │
├─────────────────────────────────────────────────────────────┤
│ 回放层   Executor：每步 → resolve → act → verify → 记录      │
│          ├ Resolver（L0-L4 阶梯）                            │
│          ├ Actuator（click/input/select/scroll/upload/drag） │
│          └ Verifier（期望效果校验）                          │
├─────────────────────────────────────────────────────────────┤
│ 采集层   Recorder：事件采集 → 快照 → 元素包 → trace         │
│          （注入脚本 + CDP 增强：closed shadow / OOPIF）      │
├─────────────────────────────────────────────────────────────┤
│ 驱动层   Playwright（v0）/ 自研 CDP client（v2 可选）        │
├─────────────────────────────────────────────────────────────┤
│ 存储层   trace.json + 元素截图 + artifact（快照/日志/报告）   │
└─────────────────────────────────────────────────────────────┘
```

**数据流**：录制时 `驱动层 → 采集层 → trace.json`；回放时 `trace.json → 编排层 → 回放层 → 驱动层`。

## 5. 数据模型：Action Trace v0

### 5.1 顶层结构

```ts
interface Flow {
  id: string
  title: string
  version: number                    // 自愈写回时 +1
  createdAt: string
  env: {                             // 录制环境快照，回放时用于告警
    startUrl: string
    viewport: { width: number; height: number }
    dpr: number
    userAgent: string
    locale: string
    timezone: string
  }
  variables: Variable[]              // { name, type:'string'|'secret', defaultValue?, source:'input'|'csv' }
  steps: Step[]
  stats?: { runs: number; passes: number; lastRunAt?: string }
}
```

### 5.2 Step 联合类型

```ts
type Step =
  | { kind: 'navigate'; url: string; expect?: Expect }
  | { kind: 'click';    target: ElementRef; button?: 'left'|'right'|'middle'; clickCount?: number; modifiers?: string[]; expect?: Expect }
  | { kind: 'input';    target: ElementRef; value: string; clear?: boolean; expect?: Expect }
  | { kind: 'select';   target: ElementRef; value: string | string[]; expect?: Expect }
  | { kind: 'key';      key: string; target?: ElementRef; expect?: Expect }
  | { kind: 'hover';    target: ElementRef }
  | { kind: 'scroll';   target?: ElementRef; delta?: { x?: number; y?: number }; to?: 'top'|'bottom'; expect?: Expect }
  | { kind: 'drag';     from: ElementRef; to: PointRef }
  | { kind: 'upload';   target: ElementRef; files: string[] }
  | { kind: 'wait';     condition: 'element'|'networkIdle'|'timeout'; target?: ElementRef; ms?: number }
  | { kind: 'assert';   target?: ElementRef; assertion: Assertion; expect?: Expect }
  | { kind: 'extract';  target: ElementRef; into: string }        // 提取文本/属性到变量
  | { kind: 'script';   code: string }                            // 逃生舱
  | { kind: 'group';    label: string; steps: Step[] }            // 子流程/嵌套
```

### 5.3 ElementRef：**这是整个产品的核心**

录制时一次点击，落一份"证据链"：

```ts
interface ElementRef {
  // ① 语义候选（按可信度排序，录制时就排好）
  candidates: Array<{
    kind: 'testid' | 'role' | 'label' | 'text' | 'css' | 'xpath'
    value: string | { role: string; name?: string; exact?: boolean }
    score: number            // 越小越可信，见 §6.2 打分表
    strict?: boolean
  }>

  // ② 结构指纹（抗改版的"身份"）
  fingerprint: {
    tag: string
    role?: string
    accessibleName?: string
    attrs: Record<string, string>      // id/name/type/placeholder/aria-*/data-*（去掉动态 class）
    stableHash: string                 // sha1(tag + role + name + 稳定属性)
    nodePath: number[]                 // 从 frame document 到元素的 childIndex 链（最后手段）
    backendNodeId?: number             // 录制时 CDP 节点 id（同 session 内快速命中；跨 session 只做校验）
  }

  // ③ 位置与几何（兜底 + 视觉匹配的锚）
  geometry?: {
    rect: { x: number; y: number; width: number; height: number }   // 相对视口
    inScrollContainer?: ElementRef                                   // 若元素在某个滚动容器里
    viewport: { width: number; height: number }
    scroll: { x: number; y: number }
  }

  // ④ frame 链（iframe 专项，见 §8.1）
  frame: FramePath

  // ⑤ 人类/AI 可读描述（AI 兜底用；也用于产品 UI 展示"这一步在点什么"）
  description?: string        // 例："顶部导航右侧的蓝色『提交』按钮"
  nearbyText?: string[]       // 邻近文本锚点："提交"左边的 label 文本

  // ⑥ 视觉兜底素材
  crop?: { ref: string; dpr: number }   // 元素裁剪截图（存 artifact 目录，不进 JSON）
}
```

### 5.5 FramePath（iframe 专项）

```ts
interface FramePath {
  path: Array<{
    kind: 'frameElement' | 'urlPattern' | 'index'
    selector?: ElementRef        // 父 frame 里 iframe 元素的引用
    urlPattern?: string          // 用 URL 模式而不是完整 URL（带 hash/token 的会变）
    index?: number               // 第几个 frame（最后手段）
  }>
}
```

回放时**逐层进入**，任何一层失败就重试等 frame 出现，而不是硬编码 `iframe#id`。

## 6. 回放算法：阶梯解析

### 6.1 每步的执行流程

```
execute(step):
  for attempt in 1..maxAttempts:
    waitForStable()                       # Playwright 的 actionability：visible/stable/enabled/receivesEvents
    el, level = resolver.resolve(step.target)   # 见 6.2
    if !el:
      if attempt < max: sleep(backoff) ; continue
      el = await repair(step.target)      # L4：AI 重定位（可选）
    act(el, step)                         # 见 6.3
    ok, evidence = verifier.check(step.expect)  # 见 6.4
    if ok: record(step, level, elapsed); return
  throw StepFailure(step, artifacts)      # 见 6.5
```

### 6.2 解析阶梯（Resolver）

| 级别 | 策略 | 成本 | 命中条件 | 抄谁 |
|---|---|---|---|---|
| **L0** | 录制时 backendNodeId 仍在且 fingerprint 匹配 | ~0ms | 同 session / 元素未重建 | browser-use `rerun_history` 的 EXACT |
| **L1** | 语义候选（testid → role+name → label → text）逐个 query，**首个唯一命中** | 1-5ms | 常规 DOM | Playwright `selectorGenerator` 打分表 |
| **L2** | 结构指纹：stableHash 相同 → 属性子集匹配 → nodePath（带容错±1）→ 邻近文本锚点（"『提交』右侧 30px 的 button"） | 5-20ms | 改版但结构未大变 | browser-use 的 STABLE hash / ATTRIBUTE 级 |
| **L3** | 视觉模板匹配：在候选区域（滚动容器/视口）内用元素裁剪截图做 NCC 多尺度匹配，阈值 + 唯一性约束 | 20-80ms | canvas / 无属性控件 | UI.Vision 思路 + OpenCV |
| **L4** | AI 重定位：把 **aria snapshot + 截图 + 目标描述** 给模型，返回 `ref` 或坐标 | 1-3s | 前面全失败 | midscene / stagehand `observe` |

**打分表（L1 用，直接抄 Playwright 的）**：

```
testid 1-2 ≪ iframe name 10 ≪ role+name 100 ≪ placeholder 120 ≪ label 140
≪ alt 160 ≪ text 180 ≪ title 200 ≪ id 500 ≪ role(无 name) 510 ≪ tag 530
≪ nth 10000 ≪ css 兜底 1e7
```

**歧义处理**：命中多个时，按 `score → 几何距离（与录制时 rect 的距离）→ 可见性 → 文本相似度` 排序取第一，但**必须记日志**（`ambiguous: 3 candidates`）；若 top1 与 top2 分数接近（差 <15%），直接降级到下一级而不是赌。

### 6.3 动作执行（Actuator）

不要直接 `element.click()`，抄 Playwright 的语义：

- **点击前**：`receives-events` 命中测试（`elementsFromPoint` 沿 shadow root 校验命中链）→ 防止"点了但点到遮罩"；
- **点击中**：捕获期 hit-target 拦截（`event.isTrusted` 过滤），layout shift 时阻断并重试；
- **输入**：用原型链 native setter 绕过 React value tracker + `dispatchEvent(input)`（page-agent 已验证的 8 行 utils）；
- **滚动**：优先滚动到元素可见（`scrollIntoViewIfNeeded`），滚动容器用 `data-scrollable` 式探测（browser-use 的滚动余量模型）；
- **上传**：走 `setInputFiles` 而不是模拟点击（受控浏览器才有这个能力）。

### 6.4 期望效果校验（Verifier）

录制时**自动推断** expect（这是相对 codegen 的明显升级）：

| 录制时观察到的变化 | 自动生成的 expect |
|---|---|
| URL 变了 | `urlChange(pattern)` |
| 出现/消失元素 | `elementVisible(ElementRef)` / `elementHidden` |
| 目标元素文本变了 | `textChange(old, new)` |
| 关键区域 DOM 结构变了 | `domDiff(region, hash)` |
| 无任何变化 | 不生成 expect（避免误判） |

回放时校验失败 → 不是"超时"，而是**语义失败**："预期跳转到 /welcome，实际仍在 /login" + 前后截图。这直接决定产品可用性。

### 6.5 失败与自愈

```
StepFailure
 ├ 分类：元素未找到 / 找到但不可交互 / 交互后无效果 / 期望不符 / 页面崩溃
 ├ artifact：before/after 截图 + aria snapshot + 候选打分日志 + 控制台错误
 └ 可选：AI 修复 → 成功后把新候选写回 trace（version+1），下次直接 L1 命中
```

**自愈即学习**：一次 AI 修复的产出不是"这次跑过"，而是"trace 变强了"。这是长期竞争壁垒——录得越多、跑得越多，成功率越高。

## 7. 录制算法（怎么采）

### 7.1 采集时机（避免录到"半稳定态"）

```
用户动作 → 等 100-300ms（防抖）→ 等 DOM stable（连续 2 帧无布局变化）
        → 采集元素包（语义候选 + 指纹 + 几何 + crop）
        → 推断 expect（对比动作前后的快照）
        → 落 trace step
```

**关键**：录制器要**先等页面稳定再采集**，否则会录到"骨架屏/加载中"的元素。这是 codegen 常见的失败原因之一。

### 7.2 采集来源（两级）

| 信息 | 来源 | 备注 |
|---|---|---|
| 事件（click/input/keydown/scroll/上传） | 注入脚本（Playwright recorder 同款）+ 轮询兜底 | 捕获 `isTrusted`，过滤合成事件 |
| 元素语义/指纹 | 注入脚本（DOM API） | role/name 走 Playwright `roleUtils` 那套 accname |
| **closed shadow / OOPIF 元素** | **CDP**：`DOM.getDocument({pierce:true})` + `DOM.getNodeForLocation` | 注入脚本进不去，只有 CDP 能看见 |
| 页面状态快照（推断 expect 用） | 注入脚本的 DOM 摘要 + aria snapshot | 复用 Playwright 的 `ariaSnapshot` |

### 7.3 事件合流（踩过的坑，直接抄）

- **双击 vs 单击**：`click` 先缓冲 300-500ms，若期间出现第二次 `click` 且目标相同 → 合并成 `doubleClick`；
- **导航竞态**：click 后 500ms 内 URL 变化 → 把 `navigate` 合并进 click 的 expect，而不是生成独立 step；
- **输入合并**：逐个 `keydown` 合成一次 `input`（等输入结束 500ms 后再落 step），否则一次输入会产生 20 个 step；
- **滚动合并**：500ms 内多次 wheel → 合并成一次 scroll delta。

> 这套合流逻辑 Playwright 已经写好了（`recorderSignalProcessor.ts` 的 `_shouldBuffer` + 500ms 缓冲），可以直接对照实现。

## 8. 难场景专项方案（你的原始痛点）

### 8.1 iframe（含跨域）

| 情况 | 方案 |
|---|---|
| 同源 iframe | 注入脚本天然进入（Playwright 每个 frame 都注入）；FramePath 用 `frameElement` 引用 + urlPattern |
| **跨域 iframe（OOPIF）** | **CDP `Target.setAutoAttach({flatten:true})` 自动挂到子 target**，每个 target 独立注入 + 独立采集；元素身份带 `(targetId, backendNodeId)` |
| iframe 动态 id / srcdoc | 不记 `#id`，记 `urlPattern` + `frameElement` 引用 + `index` 兜底 |
| iframe 内元素坐标 | 用 CDP 的 `absolute_position`（browser-use 的做法：逐层加 iframe offset），视觉兜底时用绝对坐标 |

### 8.2 closed shadow DOM

- 注入脚本**拿不到**（`element.shadowRoot === null`）；
- CDP `DOM.getDocument({pierce:true})` **能穿透**，节点有 `shadowRootType: 'closed'`；
- 方案：录制时对每个事件目标额外做一次 CDP 反查（`DOM.getNodeForLocation` 拿 backendNodeId → `DOM.describeNode`），把 (backendNodeId, 节点路径, 父宿主信息) 存进 fingerprint；回放时用 Playwright 的 `pierce` selector 或"点宿主 + 偏移"兜底。

### 8.3 canvas / WebGL / 视频 / 地图

DOM 层无解，走两级：

1. **视觉兜底（L3）**：录元素裁剪截图 → 回放时模板匹配（限定在录制时 rect 附近区域，多尺度 + 阈值 0.85 + 唯一性）；
2. **坐标兜底（L3.5）**：录相对坐标（相对 canvas 元素，而不是屏幕），canvas 尺寸变化时按比例缩放。

> 这两级**只作为兜底**，命中时要显式标记"视觉命中"，提醒用户这条 flow 更脆。

### 8.4 虚拟列表 / 无限滚动

- 不记 `nth-child`；
- 记 **item 的语义锚点**（文本/属性）+ 容器引用；
- 回放时：先滚到锚点可见（滚动 + 轮询文本匹配，最多 N 次），再点锚点本身；
- 容器滚动用"滚动余量"探测（`scrollHeight - clientHeight - scrollTop`），抄 browser-use 的 `data-scrollable` 模型。

### 8.5 SPA 重渲染 / 点击瞬间节点被替换

- 录制时同时记 `mousedown` 与 `mouseup` 的目标；回放时若节点在点击过程中消失（`isConnected === false`），重试并重新解析；
- 抄 Playwright 的 hit-target 拦截：点击过程中若布局变化，阻断事件并重试。

### 8.6 上传 / 下载 / 弹窗 / 新标签页

- 上传：录 `<input type=file>` 的引用 → 回放 `setInputFiles`（需要受控浏览器）；
- 下载：录触发元素 → 回放时监听 download 事件并保存；
- `alert/confirm/prompt`：录动作（accept/dismiss + 输入值）；
- 新标签页：录 `context.on('page')` 产生的新 page，FramePath 升级为 `PagePath`（v1 支持，MVP 可先不录）。

### 8.7 反自动化站点

- 受控浏览器默认带 Playwright 特征；
- 可选接入 `patchright` 的 patch（`../refs/patchright/driver_patches/*`）；
- **产品必须有合规边界**：不绕过验证码，遇到验证码转人工（录一个"人工接管"步骤）。

## 12. 风险与开放问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| 受控浏览器录不到用户真实浏览器的登录态/插件 | 用户觉得"录不了我平时用的" | 支持导入 cookie/profile；二期扩展模式 |
| 视觉兜底误匹配 | 点错元素，比失败更糟 | 阈值 + 唯一性约束 + 显式标注"视觉命中" |
| AI 兜底延迟/成本 | 体验差、账单高 | 只在降级后调用 + 结果写回，长期调用率下降 |
| trace 体积（截图） | 存储膨胀 | 元素裁剪图 + webp + artifact 分级保留 |
| 反自动化合规 | 法律/平台风险 | 明确不绕验证码、不做批量刷量；企业版可审计日志 |
| 录制时用户操作过快 | 漏动作/合并错误 | 录制器提示 + 事后在 timeline 上编辑补齐 |
